## Verdict

RetainDB is a young, untested TypeScript monorepo chasing the same problem as symmemory, and its `packages/local` runtime is the only part with a comparable deployment shape (one local process, file-backed store, MCP + HTTP + CLI). Nothing transfers as code (TS→Go, and no license need arises since all findings are pattern-level), but four mechanisms in their local retrieval/context loop are genuinely ahead of ours: retrieval reinforcement, ingest-time signal gating, delta context packs, and full-lifecycle capture hooks. The single highest-value takeaway is the **retrieval feedback loop** — access counts that strengthen reused memories and a decay pass that retires never-recalled weak ones — because our current scoring ages every memory at the same rate regardless of use. Treat all upstream constants as arbitrary (untested repo); adopt the mechanisms, re-derive the weights with our own bench harness.

## What we already do as well or better

- RRF hybrid fusion (their `packages/local/src/cli.ts:900-904`) → already implemented in `internal/db/hybrid.go:81` (`ReciprocalRankFusion`) and `:182`; serving it everywhere is already scoped in issue #391.
- Hash-vector embedding fallback (their `EMBEDDING_PROVIDER=hash`, `cli.ts:104`) → we already ship the FNV-1a hash fallback behind the same Ollama-first design.
- Retrieval benchmarking (their 4-fixture smoke bench `cli.ts:2720-2763`) → `internal/bench/` is strictly stronger: Recall@k/NDCG/MRR, LongMemEval corpus, abstention threshold.
- Privacy screening at ingest (they have none — only a low-signal filter) → `internal/security` PII Guard redacts before storage; nothing comparable upstream.
- Temporal validity and versioning (their server-side `validFrom`/`validUntil`) → `valid_from`/`valid_until` + `superseded_by` + as-of queries (`internal/db/hybrid.go:141`, `cmd/list_asof_test.go`).
- Durable at-rest protection → our AES-256-GCM encrypted sync relay and encrypted backup vs. their plaintext `local-store.json` snapshot + JSONL journal under `~/.retaindb/`.
- MCP stdio discipline → their MCP package is an HTTP bridge (`packages/mcp/src/server.ts`); our native stdio server with zero-stdout-pollution is the stricter design.
- Payload-bounded/cursor-addressable reads → our HTTP handlers already cursor-paginate (`internal/mcp/handlers.go:181-186`); upstream has `top_k` only. Bounding MCP reads further is already issue #401.

## Findings

- [ ] **[Architecture] Add a retrieval feedback loop: access reinforcement plus decay-aware consolidation**
  - **Status quo:** Our composite score (`internal/db/memory.go:984-1000`) blends relevance, recency (exponential age decay, half-life 30d) and a static importance value — a frequently reused two-year-old decision sinks at exactly the same rate as a never-read two-day-old note, and nothing in `internal/consolidation/` ever retires a memory that has literally never been recalled. RetainDB Local tracks `access_count`/`last_access` per memory, increments both on every retrieval hit (`packages/local/src/cli.ts:910-912`), feeds `log1p(access_count)` reinforcement and a strength/age decay term into ranking (`cli.ts:883-885`), and its consolidation pass deactivates non-durable memories older than 14 days with zero accesses and strength < 0.45 (`cli.ts:1446-1456`). Motivation is documented in their README ("Reinforce memories that get reused") but the constants are unvalidated — no tests exist upstream.
  - **Proposed solution:** Pattern adoption. Add `access_count` and `last_accessed_at` columns (SQLite migration), update them in the search/get paths, and add a configurable reinforcement term to `CompositeScore` alongside the existing recency term (recency stays — reinforcement rewards *use*, recency rewards *freshness*). Extend consolidation with a deterministic decay rule: old + never-accessed + low-importance non-durable memories become inactive (tombstoned, not deleted, so sync/audit semantics hold). Re-derive weights with `internal/bench/` rather than copying theirs; keep the term behind `RankingWeights` config so it is reversible.
  - **Effort/Impact:** Medium effort / high impact. One schema migration plus scoring and consolidation changes; fully reversible via config weights (set reinforcement to 0 to restore current behavior). Directly improves long-lived-store ranking, which is our core product promise.

- [ ] **[Architecture] Gate ingest with a deterministic low-signal quality scorer**
  - **Status quo:** Today any string that passes the PII Guard lands in the store — `cmd/set.go` and the `memory_set` path in `internal/mcp/handlers.go` have no semantic quality gate, so noise ("ok", "thanks", "session_start captured", raw build-log dumps) dilutes recall and gets embedded, indexed, and synced. RetainDB Local scores every candidate at ingest with a deterministic `signalQuality` heuristic — low-signal regexes (`packages/local/src/cli.ts:91-96`), code-path/decision/outcome/structure bonuses, noise penalties (`cli.ts:149-160`) — and below a type-dependent threshold stores an *inactive* `skipped` record with `reason: "low_signal"` and the quality score (`cli.ts:673-690`), so nothing vanishes silently; the same quality value later modulates ranking (`cli.ts:904`).
  - **Proposed solution:** Pattern adoption. Add a small pure-Go scorer (regex + token features, no LLM, no deps — CGO-free constraint holds) evaluated in the `set`/`memory_set`/importer ingest paths after PII redaction. Below-threshold candidates are stored inactive with `skipped` metadata (mirrors the spirit of issue #396: mutations must be reported, not silent) and excluded from retrieval by the existing `active` filter. Surface the score in `get`/explain output. Constants re-tuned against our bench corpus, not copied.
  - **Effort/Impact:** Low effort / medium-high impact. One new file plus a gate call in three ingest paths; reversible (threshold 0 disables). Pairs with the lifecycle-capture finding below — live capture without a signal gate would import noise at scale — and removes a whole defect class (store pollution) rather than individual bad memories.

- [ ] **[Architecture] Extend agent hooks from SessionStart injection to full-lifecycle live capture**
  - **Status quo:** `cmd/hook.go:28-60` generates exactly one hook — Claude Code `SessionStart` — and it only *injects* context; everything our store knows about a session arrives post-hoc via the `internal/importer/` package (claudecode/codex/opencode JSONL), which requires a manual import run and loses event timing. RetainDB ships a 12-point lifecycle hook set (`packages/local/plugin/hooks/hooks.json:2-16`: `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PreCompact`, `SubagentStart/Stop`, `SessionEnd`, …) whose scripts POST salience-tagged work events to a `/retaindb/observe` endpoint (`packages/local/src/cli.ts:1871`, shared capture helper `packages/local/plugin/scripts/_capture.mjs:55-84`) and inject a compact context pack on prompt submit and pre-compact. Note: the parallel mem0 adopt report (`docs/adopt/2026-07-30T12-32-40Z--mem0ai-mem0.md:69`) rejected this pattern at gate 3 because "#400 already plans source-linked session context" — but #400 scopes *storage and lineage* of session events, not the *capture transport*; our repo has already accepted shipping hook configs as in-scope (`cmd/hook.go` exists), and the capture direction is the missing half.
  - **Proposed solution:** Pattern adoption. Grow `symmemory hook claude-code` into a lifecycle set: add `PostToolUseFailure`, `SessionEnd`, and `PreCompact` hook blocks that call new fail-safe CLI subcommands (e.g. `symmemory observe --kind fix --salience high`) writing session-scoped, PII-guarded events — reusing the existing ingest path plus the signal gate from the finding above. Keep the fail-safe discipline already in `hook.go` (never exit non-zero, never pollute stdout). `PostToolUseFailure` first: tool failures are the highest-signal correction memories and the ones importers most often lose.
  - **Effort/Impact:** Medium effort / high impact. Additive hook JSON plus one new write-path subcommand; fully reversible (hooks are opt-in config). Feeds the event stream that issue #400's session layer will need anyway, and turns consolidation input from "whatever was manually imported" into "what actually happened".

- [ ] **[Performance] Offer delta context packs via content-hash snapshots**
  - **Status quo:** Every `symmemory context` call re-assembles and re-emits the full block (`internal/contextassembler/assembler.go:60-151`, `cmd/context.go:60-75`); an agent injecting context on every prompt re-receives all unchanged sections every turn, paying the full token cost each time. RetainDB's context pack hashes each section, keeps a ring of 80 snapshots, and when the caller passes `previous_context_hash` returns only `delta_context` plus explicit `changed`/`removed` lists (`packages/local/src/cli.ts:1296-1332`); their hook helper threads the hash per session (`packages/local/plugin/scripts/_capture.mjs:60-78`). The mechanism is plain hashing — no infra, CGO-free, trivially portable.
  - **Proposed solution:** Pattern adoption. Store a bounded snapshot ring (per project+session, e.g. 80 entries) of `{hash, piece-hashes}` in a small SQLite table; add optional `--previous-hash` / `previous_hash` to `cmd/context.go` and the context assembler output (`context_hash`, `delta_context`, `changed`, `removed`, `estimated_delta_tokens`). Default behavior unchanged; the SessionStart hook can thread the hash through an env var exactly as upstream does. Validate the token saving with the canary harness planned in issue #402 before documenting any reduction number.
  - **Effort/Impact:** Medium effort / medium impact. New table plus delta computation in the assembler; opt-in and reversible (omit the flag, get today's behavior). Complements #401 (bounding) and #402 (canaries) but solves a different problem: change-detection across calls, not payload size per call.

- [ ] **[UX/DX] Make doctor recommend the next command, not just report state**
  - **Status quo:** `cmd/doctor.go:30-60` prints ✅/⚠/❌ per check with a detail string but never names a remediation — zero `recommend`/`run` hints in 409 lines — so a user seeing "1,234 memories" or a warning has to know which command fixes which symptom. RetainDB's `inspect` derives store-shape signals (durable-memory ratio < 0.25, stale never-recalled memories, duplicate groups) and prints the exact next command for each (`packages/local/src/cli.ts:1157-1161`: "Run `retaindb consolidate` …", "Run `retaindb connect all --install` …").
  - **Proposed solution:** Pattern adoption. Add two or three derived checks to `cmd/doctor.go` — duplicate-candidate count, never-recalled-and-old count (uses the access columns from the first finding; degrade gracefully until they exist), durable ratio — and append a `Next steps:` section naming the concrete command (`symmemory dream`, `symmemory hook claude-code --merge`) per finding. No new dependencies.
  - **Effort/Impact:** Low effort / low-medium impact. Trivially reversible, self-contained in one file; converts doctor from a status page into a runbook and measurably shortens the "something is off — what do I run?" loop.

## Considered and rejected

- **Serve RRF-fused hybrid retrieval** — gate 2 (New): already implemented in `internal/db/hybrid.go:81,182` and already scoped as open issue #391 (which a prior adopt report generated); nothing to re-propose.
- **Memory graph with typed relations (`updates`/`contradicts`/`supports`/`extends`/`derives`)** — gate 2 (New): entities + provenance relations + temporal intervals already exist (`internal/entity/`, `entity_relate` in `internal/mcp/mcp_tools.go:113`).
- **Temporal validity (`validFrom`/`validUntil`) and versioned memories** — gate 2 (New): `valid_from`/`valid_until`, `superseded_by`, as-of queries (`cmd/list_asof_test.go`).
- **Hash-vector embedding fallback** — gate 2 (New): FNV-1a fallback already ships (same Ollama-first design).
- **Their `retaindb benchmark` smoke bench** — gate 3 (Better): 4 hand-written fixtures with hit-rate + percentiles (`cli.ts:2720-2763`) is strictly weaker than `internal/bench/` (Recall@k/NDCG/MRR, LongMemEval, abstention).
- **Connectors (GitHub, Notion, Slack, Confluence, PDF, sitemap…)** — gate 1 (Transferable): requires external API keys/services and conflicts with the standalone-first constraint; the `internal/importer/` file-based importers cover the local demand.
- **The whole `packages/server` platform (Postgres+pgvector, Prisma, ingestion queues, dashboards, plan-based rate limits, cloud auth)** — gate 1 (Transferable): different deployment shape, and AGENTS.md forbids cloud/tenant/billing features in this repo.
- **Redis-backed per-plan rate limiting (`packages/server/src/middleware/rate-limit.ts`)** — gate 4 (Worth it): Redis dependency plus tenant plans are Pro-repo concerns; the local JWT-bound loopback daemon has no recorded abuse pain.
- **API idempotency keys (migration `20260226_add_api_idempotency`)** — gate 3 (Better): entity relations are already idempotent via source+source_ref, sync uses LWW oplog tombstones; no recorded duplicate-write pain on `memory_set`.
- **Session replay viewer with `elapsed_ms` step-through (`cli.ts:1358-1385`)** — gate 3 (Better): no recorded demand; our web console already covers session inspection, and issue #400's planned session layer will define the real replay surface.
- **Payload-bounded MCP reads** — gate 2 (New): already covered by open issue #401.
- **Neural/cross-encoder reranking (their second-pass `rerank`, `cli.ts:936-955`)** — gate 4 (Worth it): their rerank is a heuristic term bump, not a cross-encoder; our first finding already adds the valuable signals (reinforcement, quality), and #391 explicitly scopes reranker changes out. Revisit only if bench shows a gap after the feedback loop lands.
- **`connect all --install` multi-agent config writer** — folded into the lifecycle-hooks finding rather than a standalone finding; alone it is gate 3 (marginal delta over `hook --merge`).

## Open questions

- Upstream's reinforcement/decay constants (`log1p(access_count)/5`, strength bump `+0.03`, decay rule `ageDays > 14 && accessCount == 0 && strength < 0.45`) have no tests or rationale commits visible (shallow clone, no CI, young repo). What weights survive our `internal/bench/` + LongMemEval harness is an empirical question — the finding is for the mechanism, not the numbers.
- Whether `PostToolUseFailure`-style live capture produces enough *useful* events to beat the noise floor — measurable only after the signal gate exists; the two findings should land together or gate-first.
- The README advertises "Apache 2.0 / BSL 1.1" dual licensing, but only an Apache-2.0 LICENSE ships in the repo; whether `packages/server` is intended to be BSL is undocumented. All findings here are pattern-level so this does not block anything, but it forbids verbatim copying until clarified.

Best first step: land the low-signal ingest gate — it is the cheapest finding, self-contained in the ingest path, and it is the precondition that makes lifecycle live capture safe to turn on.
