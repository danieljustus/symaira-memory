## Verdict

mem0 is the most popular open-source memory layer for AI agents — and shares the same basic mission as our TARGET — but the two repos have diverged in architecture and constraints. mem0 is Python+TypeScript with a FastAPI+PG server and managed vector stores, while the TARGET is a CGO-free single Go binary with SQLite and zero external dependencies. The highest-value transfer is a small, precision pattern from mem0's LLM pipeline: anti-hallucination ID mapping when presenting memory IDs to an LLM for update decisions. A secondary transfer — enabling FTS5 porter stemming for BM25 keyword recall — is cheap and measurable with our existing bench harness. Both are pattern-only adoptions.

## Findings

### Architecture

- [ ] **[Architecture] Map real memory IDs to short integer indices when presenting them to the LLM in the consolidation prompt**
  - **Status quo:** `internal/consolidation/engine.go:449` passes raw memory UUIDs (`m.ID`) verbatim into the LLM prompt, and `engine.go:200-203` relies on the LLM echoing them back in `replaces_ids`. When the LLM truncates, mangles, or hallucinates a UUID — a known failure mode for long opaque tokens — the returned ID does not match any real `m.ID` and the memory is silently **not archived** (the `parentID := summary.ReplacedIDToNewID[m.ID]` lookup at line 234 returns `""`, `isReplaced` stays `false`, and the memory stays in raw state with no warning). Upstream `mem0/memory/main.py:903-908` handles exactly this: search results' UUIDs are mapped to small integer strings (`"0"`, `"1"`, …) before the LLM sees them, then reverse-mapped via `uuid_mapping` when processing the response. The commit introducing this includes the explicit comment `# Map UUIDs to integers (anti-hallucination)`. The same UUID → int pattern also reduces token consumption in the prompt.
  - **Proposed solution:** In `consolidateWithLLM` (engine.go:448), assign each memory a short integer key (`"0"`, `"1"`, …) instead of its raw UUID. Build a forward map `key → m` and a reverse map `key → m.ID` before passing to the LLM. On the return side (engine.go:200), use the reverse map to resolve `replaces_ids` back to real UUIDs. Pattern adoption only; no code copy. The existing `txMemMap` logic stays unchanged.
  - **Effort/Impact:** Low effort / medium impact. The change touches ~15 lines in `engine.go` — no new dependencies, minimal tests. Reversible; the old path (raw IDs) can stay as a comment. Solves a silent failure class in the core consolidation pipeline.

### Performance

- [ ] **[Performance] Enable SQLite FTS5 porter tokenizer for stem-normalized BM25 keyword search**
  - **Status quo:** `internal/db/migrations/016_fts5.sql` creates the FTS5 virtual table with the default `unicode61` tokenizer — no stemming. `SearchMemoriesBM25` (`internal/db/hybrid.go:95`) matches only exact tokens: a query for "running" does not retrieve memories containing "run". Upstream `mem0` explicitly lemmatizes text for BM25 (`mem0/memory/main.py:996`, `lemmatize_for_bm25` at 1930). SQLite FTS5 ships with a built-in `porter` tokenizer (Porter stemming algorithm) that can be combined with `unicode61`.
  - **Proposed solution:** Rebuild `memories_fts` with `tokenize='porter unicode61'`. This requires a migration that drops the existing virtual table, recreates it with the new tokenizer, and backfills the FTS index from existing `memories` rows. The underlying content table and triggers remain unchanged. The improvement is directly measurable via the existing retrieval bench harness at `internal/bench/` (Recall@k metric — open issue #399 plans to run it weekly, making the delta verifiable). Pattern adoption only.
  - **Effort/Impact:** Low effort / medium impact. The backfill is a one-time Go migration that inserts existing memory content into the new FTS table. No new dependencies. Reversible (table can be dropped and recreated with the old tokenizer). The bench harness can confirm the recall improvement before and after.

## Considered and rejected

- **Batch embedding API with per-item fallback** — gate 4 (Worth it): mem0's `embed_batch` with graceful per-item degradation (`main.py:964-973`) is a real optimization, but the TARGET's importer runs once per import and import speed is not a recorded pain point. Revisit if bulk-import performance becomes a bottleneck.
- **Rich metadata operator filters on search (`gt`, `lt`, `contains`, `AND`/`OR`/`NOT`)** — gate 3 (Better): no recorded pain point — the TARGET's local SQLite backend means advanced users can query the database directly. The existing search API (scope + entityID + semantic/keyword + trust/policy) covers the primary use cases without operator-bloated query surface.
- **Two-tier skill structure (reference + pipeline)** — gate 2 (New): the TARGET already has an open finding (#392) to ship a single agent skill artifact. mem0's multi-skill structure is an implementation detail for that issue, not a separate finding.
- **Reranker stage after search** — gate 2 (New): already covered by `rank_search_results.go` + open issue #391 (hybrid fused retrieval).
- **History/audit versioning of memory mutations** — gate 2 (New): the TARGET already has audit log, provenance tracking, evidence spans, and sync oplog — richer than mem0's `history` table.
- **Telemetry sampling with first-run notices** — gate 1 (Transferable): the TARGET is purpose-built as a self-hosted, zero-call-home tool (AGENTS.md); telemetry infrastructure would violate its privacy contract.
- **Graph memory (Neo4j)** — gate 1 (Transferable): requires a Neo4j server, violating the CGO-free standalone constraint. Entity relations + temporal provenance already cover graph-like queries in SQLite.
- **CI matrix gating via path filters** — gate 3 (Better): mem0's 25-workflow CI suite serves a multi-ecosystem monorepo with 7+ independent packages. The TARGET is a single Go binary; its two-workflow CI (ci.yml, release.yml) is already minimal and fast. No delta.
- **LLM error distinction (unavailable vs empty-result)** — gate 2 (New): the TARGET's consolidation engine already isolates per-scope failures (`reportScopeFailures` at engine.go:438) and the langextract adopt finding hardened the response parser. The distinct error path is already handled.
- **Self-hosted FastAPI server with PostgreSQL/pgvector** — gate 1 (Transferable): incompatible with the CGO-free, standalone-first constraint that keeps a single SQLite binary deployable with no infrastructure.
- **Past-message truncation for LLM context budget** — gate 3 (Better): mem0's `PAST_MESSAGE_TRUNCATION_LIMIT` and `_truncate_content` prevent context overflow in the extraction LLM call. The TARGET consolidation engine processes per-scope batches; memory content is typically short facts. No open issue or recorded pain about context overflow in consolidation. Revisit if context-pressure canaries (#402) detect overflow in production.
- **MCP plugin with agent lifecycle hooks (session-start injection, post-tool capture)** — gate 3 (Better): the pattern is client-side (the agent's editor framework decides hooks); open issue #400 already plans source-linked session context. No delta beyond what #400 scopes.
- **Cross-tool linker with mem0 scope** — gate 2 (New): the TARGET's `Linker` (`internal/consolidation/linker.go`) already links across tools including `"mem0"` as one of `allToolScopes`.

## Open questions

- The recall improvement from porter stemming on our BM25 arm is measurable but has not been tested — the existing bench harness (`internal/bench/`) with LongMemEval corpus provides the baseline. Implement the porter migration on a branch, run `make bench` before and after, and ship only if Recall@k increases on the keyword arm.
- How often do LLM-ID mismatches actually occur in practice in our consolidation? A regression-test trace could confirm the frequency: add a log line when `parentID` is empty for a memory that should have been matched (i.e., when a consolidated memory's `replaces_ids` contains an ID that does not match any memory in the scope).
