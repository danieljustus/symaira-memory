## Verdict

Honcho is a managed/self-hosted memory FastAPI service (AGPL-3.0) with a very different architecture (Python+Postgres+Redis, client SDKs for Python/TS) from the TARGET (CGO-free Go, SQLite WAL, CLI+TUI+MCP). The language and runtime gap kills most code-level transfer, but Honcho's agent-facing search tool design (temporal filters, exact substring grep) and structured-output discipline answer two open TARGET issues directly (#397, #393). The top takeaway is **temporal + exact-text search filters** — adding `after`/`before` date bounds and a `LIKE`-based substring search to `symmemory search` and the MCP/HHTP search endpoints would unblock issue #397 and give agents precise recall they currently lack.

## Findings

- [x] **[UX/DX] Add date-range and exact-substring search filters to CLI/MCP/HTTP endpoints**
  - **Status quo:** Agents and users have no way to search memories by a date range (`created_at BETWEEN ? AND ?`) or find exact text matches (names, error codes, serial numbers). The existing search — `internal/db/hybrid.go:158` (`HybridSearch(queryVec, queryText, scope, limit)`) — is vector+BM25 only, with no temporal or substring capabilities. The CLI (`cmd/search.go:22`) supports only a `--max-age` relative filter (trust post-filter), not absolute date bounds or grep. Open issue #397 ("time-window search filter") records the demand. Honcho solves both with three dedicated dialectic agent tools: `grep_messages` (`src/crud/message.py:946` — case-insensitive substring `ILIKE` with context-window snippets), `get_messages_by_date_range` (`src/utils/agent_tools.py:615` — explicit start/end timestamps), and `search_messages_temporal` (`src/utils/agent_tools.py:643` — semantic search + date range combined). The tools are live (wired in Dialectic tool loop, tested in `tests/`). Introduced per their CLAUDE.md (reasoning levels specify which tools are available at each tier) — motivation: LLM agents need precise temporal recall that embedding similarity alone cannot provide.
  - **Proposed solution:** Pattern adoption. Add optional `after`/`before` (RFC3339) parameters and an optional `substring` parameter to `internal/db/hybrid.go:HybridSearch` and the search CLI + MCP tool. The date filter adds a `WHERE created_at BETWEEN ? AND ?` clause. The substring search queries `WHERE content LIKE '%?'` (case-insensitive via `LOWER()`). Expose via `cmd/search.go` (`--after`, `--before`, `--substring` flags) and the MCP `memory_search` tool schema in `internal/mcp/server.go`. Keep the existing vector/BM25 pipeline; both filters are additive (result intersection). Implementation effort is low — SQLite handles both operations efficiently with indexes.
  - **Effort/Impact:** Low effort / high impact. Unblocks #397 directly. Gives agents precise recall (exact names, code references, history queries) that embedding search cannot provide without configuration. Reversible: all flag additions are backward-compatible — defaults remain unchanged.

- [x] **[Architecture] Schema-first structured output with multi-stage repair fallback**
  - **Status quo:** The LLM consolidation prompt (`internal/consolidation/engine.go:464`) embeds a JSON schema description, and the Ollama client (`internal/llm/client.go:87`) sends `response_format: {"type": "json_object"}` — but there is no provider-native schema *constraint*, and on parse failure the salvage (`engine.go:546`) has no graceful degradation (a bad response logs a scope failure and continues). Open issue #393 asks for "JSON-schema-constrained LLM responses". Honcho implements a layered approach: `structured_output_mode` config (`src/config.py:140-176`, CHANGELOG #820) supports `"json_object"` fallback for providers without native structured outputs; `schema_instruction()` (`src/llm/structured_output.py:15-30`) appends the JSON schema to the system prompt; `repair_response_model_json` (`src/llm/structured_output.py:35-76`) applies multi-strategy JSON repair (partial parse, context-aware closure, line reconstruction, regex fixes) then Pydantic validation; and on total failure returns an empty `PromptRepresentation(explicit=[])` instead of crashing (`structured_output.py:69-76`). The motivation is documented in their changelog (#820 — "json_object mode for OpenAI-compatible providers that lack native Structured Outputs support") and source comments about provider compatibility. Ollama supports `format` with a JSON schema (constrained decoding) — the TARGET can use this directly.
  - **Proposed solution:** Pattern adoption. Add a config option (e.g. `LLM.StructuredOutputMode`) defaulting to `"json_schema"` (Ollama's native `format: <schema>` constrained decoding) with `"json_object"` fallback. Keep the existing salvage pipeline as the final safety net. Add a graceful empty-result fallback to `consolidateWithLLM` so a single bad LLM response returns an empty result instead of failing the scope. This directly addresses #393 without changing the provider abstraction — `internal/llm/client.go` already supports dynamic request bodies.
  - **Effort/Impact:** Medium effort / high impact. Unblocks #393. Constrained decoding eliminates malformed JSON entirely when possible (Ollama's `format` guarantees valid JSON matching the schema), reducing consolidation failures to true provider outages. The empty-result fallback prevents a single LLM glitch from failing an entire scope.

- [x] **[UX/DX] Ship MCP instructions and agent skill as versioned repo artifacts**
  - **Status quo:** There is no agent-facing instruction file or skill definition shipped in the TARGET repo. MCP clients discover tools dynamically (no `instructions.md` served alongside them), and Hermes agents have no versioned skill file to reference as a repo artifact. Open issue #392 requests exactly this: "ship agent skill as repo artifact". Honcho provides two concrete examples: `.claude/skills/honcho-cli/SKILL.md` (a self-describing skill file with usage rules, output formats, and command groups) and `mcp/instructions.md` (a separate instructions file served via the MCP server's `instructions` endpoint, describing the recommended conversation flow with tool call ordering and good/bad query examples). The files are versioned in-repo and distributed as part of releases, solving the "docs drift" problem. Motivation: inferred from the pattern — skill files give any MCP-capable agent a consistent, versioned onboarding path.
  - **Proposed solution:** Pattern adoption. Create a `.claude/skills/symmemory/SKILL.md` file documenting the symmemory MCP tools, recommended usage patterns, and common pitfalls. Create a `docs/agent-instructions.md` or serve a `<server>` instructions resource from the MCP stdio server (as defined by the MCP spec's `instructions` capability). Both are versioned in the repo and ship with the binary. Addresses #392 directly. No code changes needed in the MCP server (instructions are documentation, not code).
  - **Effort/Impact:** Low effort / medium impact. Unblocks #392. Provides a discovery surface for agent frameworks and keeps agent guidance in sync with the code. Reversible: purely additive documentation.

- [x] **[Architecture] Write-time exact-content deduplication with reinforcement counter**
  - **Status quo:** The TARGET detects duplicates at consolidation time (supersede via LSH buckets in `internal/consolidation/linker.go:91-202`) and at prep time (evidence_hash SHA-256 for memory facts, `internal/memory/prep.go:336`). But there is no **insert-time** exact-content dedup — identical facts can accumulate between dream runs, and the retrieval ranker has no reinforcement signal to prefer frequently-repeated facts over one-offs. Honcho solves this with exact-match deduplication at document creation (`src/crud/document.py:434-452`) that normalizes content (strip+lowercase), never crosses conclusion levels, and on exact match atomically increments `times_derived` instead of inserting a new row (`src/crud/document.py:171-193` orders queries by `times_derived DESC, created_at DESC`). The motivation is documented in their CHANGELOG (#768 — without reinforcement stale conclusions freeze to the front, #861 — exact dedup before semantic dedup).
  - **Proposed solution:** Pattern adoption. Add a content SHA-256 dedup check at memory insert time (`internal/memory/prep.go` or the SQL `INSERT ... WHERE NOT EXISTS` path). Add a `times_reinforced` counter (or reuse the existing `importance` field) that increments on dedup match. Adjust the retrieval ranker (`internal/db/ranker.go`) to prefer reinforced results as a secondary ranking signal after similarity/schema score. This reduces consolidation pressure (fewer near-duplicates to clean) and improves retrieval quality (frequently restated facts surface naturally).
  - **Effort/Impact:** Medium effort / medium impact. Schema extension (new column or repurposed field), insert-path change, ranker adjustment. Reduces consolidation churn and improves top-k relevance for repeated facts. Reversible; dedup can be disabled via config.

- [x] **[Performance] Store retrieval benchmark baseline snapshots for CI regression detection**
  - **Status quo:** The TARGET has a comprehensive retrieval bench harness (`internal/bench/harness.go`, `internal/bench/metrics.go`) with Recall@k/NDCG/MRR metrics and the LongMemEval corpus. Issue #399 requests a "weekly bench CI job". Currently, metrics are computed on each run without comparison to a stored baseline — a weekly job would report absolute numbers without indicating regressions. Honcho maintains per-dataset baseline scripts (`tests/bench/locomo_baseline.py`, `tests/bench/beam_baseline.py`) that compare current results against published baselines, with the output used in their evals marketing. The motivation is inferred: baseline comparison turns a metric run into a regression test.
  - **Proposed solution:** Pattern adoption. After the weekly bench CI job (#399), store the resulting Recall@k/NDCG/MRR for the LongMemEval corpus as a JSON baseline file (`internal/bench/baseline.json`) in the repo. On subsequent runs, compare current metrics against the stored baseline and flag drops (e.g. >5% NDCG regression). This turns the weekly job from a dashboard into a regression gate. Publish baseline updates via release commits.
  - **Effort/Impact:** Low effort / medium impact. Baseline format is just JSON; comparison is a simple delta check. Adds confidence to #399's weekly job. Small maintenance surface. Reversible.

## Considered and rejected

- **Dialectic chat/QA endpoint (peer-level NL question answering with tool loop)** — gate 4 (Worth it): builds and owns an agent-loop surface (streaming, tool orchestration, reasoning levels). The TARGET's MCP tool surface lets frameworks drive their own tool loops; adding a chat endpoint that internally runs a tool loop would duplicate framework functionality (OpenAI tool-calling, the agent framework) and increase maintenance surface.
- **Deriver queue with Redis/Postgres background processing** — gate 1 (Transferable): relies on Postgres LISTEN/NOTIFY + Redis pub/sub; the TARGET has no background queue infra (consolidation is CLI-triggered). Adding a background deriver in Go+SQLite would require a lightweight worker abstraction — principle worth noting but the specific mechanism does not transfer.
- **Two-tier incremental LLM summarization cadence (short every 20 msgs, long every 60)** — gate 3 (Better): the TARGET's summarizer is deliberately extractive (no LLM dependency, standalone-first). No recorded pain for abstractive summaries; the existing `SummaryTokens` config and `SummarizeSession` achieve the goal within the standalone constraint.
- **Webhook system with SSRF guard (private-IP rejection)** — gate 1 (Transferable) + gate 3: the TARGET has no callback/outgoing-webhook surface; sync relay is operator-config URL, not user-provided. No user-supplied URL surface to harden.
- **Peer/workspace multi-tenancy (scoped JWTs, peer-level auth)** — gate 1 (Transferable): AGENTS.md forbids tenant/hosted features. The TARGET is single-user local daemon — JWT with RoleReadWrite is sufficient.
- **Telemetry pipeline (cloudevents, Sentry, Langfuse integration)** — gate 1 + gate 4: hosted-service features. Self-hosted TARGET has no telemetry infrastructure and should not add one.
- **Extensive CI matrix (Fly deploy, GCP registry, live LLM tests with Postgres service)** — gate 4 (Worth it): heavy infra for a standalone Go CLI. TARGET CI is already effective (GoReleaser, cross-platform builds, test CI). Honcho's `dorny/paths-filter` pattern is generally useful but already present in some TARGET workflows.
- **Prompt cache prefix optimization (stable system prompt prefix for higher cache hit rates)** — gate 3 (Better): Ollama's local KV cache already benefits from stable prefixes; the TARGET's consolidation prompt is mostly static. No measured bottleneck or recorded pain (no open performance issues for consolidation latency).
- **Read-only DB session mode for SELECT-only windows** — gate 2 (New): SQLite WAL mode already provides non-blocking reads. No transaction held across SELECTs.
- **JWT narrowest-claim authorization (peer/session scoped tokens can't widen to workspace)** — gate 2 (New): the TARGET's single-user daemon has a simpler auth model (RoleReadWrite). Multi-level scoped tokens would add complexity for no benefit in a local-only daemon.
- **Discussion categories/cadence for benchmark result communication** — gate 4 (Worth it): Honcho uses baselines for evals marketing. The TARGET needs regression detection, not published comparison docs. The baseline-storage finding above covers the actionable part.
- **Route-policy regression test (allowlist of routes with member-read flag enforced by CI test)** — gate 2 (New): the TARGET already has declarative per-route auth in `internal/mcp/http_server.go:55-84` — `routeAuth` enum is more direct than Honcho's per-route-decorator + external allowlist approach.

## Open questions

- **How does Honcho's retrieval compare quantitatively to TARGET's for equivalent recall tasks?** Both have LongMemEval; a cross-run comparison would be informative but does not affect adoption decisions.
- **Honcho's `grep_messages` supports a `context_window` parameter returning neighbor messages.** The TARGET could adopt the same pattern for substring search. Worth deferring to the implementation phase (#397 design).
- **Honcho's `times_derived` is per-document.** The TARGET may prefer to express reinforcement through the existing `importance` field rather than a new column. Evaluate during implementation.
